/to-spec and /to-tickets: the multi-session branch of the flow.

Sources: to-spec (guide), to-tickets (guide), commit 5beb35b.

Where you areRun

/to-spec: a decision record

  • No interview. It synthesizes the conversation, the codebase, GLOSSARY.md and the ADRs. Anything in it you never said is a defect.
  • Seams first. It prefers existing seams, uses the highest one, and the ideal number is one. You confirm them. /tdd and /code-review build on them later.
  • Sections: Problem Statement · Solution · User Stories (a long list) · Implementation Decisions · Testing Decisions · Out of Scope · Further Notes.
  • No file paths or code snippets, except a snippet a prototype produced that encodes a decision.
  • Read closely: the seams and Out of Scope.
  • The spec is a snapshot that goes stale and can be thrown away after the work ships. What should last goes in GLOSSARY.md and ADRs.

/to-tickets: tracer bullets

  1. A narrow but complete path through every layer (schema, API, UI, tests)
  2. Demoable or verifiable on its own
  3. Fits in one fresh context window
  4. Prefactoring first: make the change easy, then make the easy change

Ask about every ticket: "What can I demo when this is done?" If the answer is a layer, it's a horizontal slice. If you have too many tickets, merge them.

Wide refactor exception (one mechanical change with a huge blast radius): expand by adding the new form beside the old, migrate in batches with one ticket each, all blocked by the expand, then contract by deleting the old form in a ticket blocked by every batch.

Blocking edges

  • Each ticket says Blocked by: … or "None (can start immediately)".
  • Frontier = tickets whose blockers are all done. Open one fresh session per frontier ticket.
  • The agent quizzes you before publishing. Check the granularity, whether each edge is real, and what to merge or split.
  • Local tracker: .scratch/<feature>/issues/NN-slug.md, blockers first, so /implement 03 works. GitHub: native --blocked-by links, with tickets as sub-issues of the spec.
  • Every acceptance criterion must fail at the base commit. Name the observation that would show it false.

Gotchas

  • Don't clear or compact between /to-spec and /to-tickets, because a big spec can truncate when it's fetched back.
  • The spec also gets ready-for-agent. AFK pollers will try to build the whole thing, so exclude it or remove the label.
  • Dispatch is manual, and /implement doesn't reliably close tickets. Update their state yourself.
  • Don't run /triage on tickets /to-tickets made. They're agent-ready by construction.
