Build Card

/implement, /tdd and /code-review: one ticket, one run.

Sources: implement (guide), tdd (guide), code-review (guide), commit 5beb35b.

One /implement run

  1. Fetch the ticket, state its title, and work out the seams. There's no interview and no re-planning.
  2. /tdd at the pre-agreed seams, one red → green slice at a time
  3. Typecheck often, and run single test files
  4. Run the full suite once, at the end
  5. /code-review, then commit to the current branch

One ticket per run, with /clear between runs. You create the branch, and you close the ticket, which is what opens the frontier. For parallel work, use /implement-spec (worktrees), not several sessions in one checkout. A non-trivial ticket can use over 100k tokens. If it's much more than that, split the ticket.

/tdd

  • Seam = the public boundary where you observe behaviour. No test at an unconfirmed seam.
  • Red → green: one failing test, then just enough code to pass it, then repeat. No refactor phase (removed June 2026). Refactoring belongs to /code-review.
  • A good test reads like a spec, uses the public API only, and survives refactors.
  • Mock system boundaries only: external APIs, time, randomness, and sometimes the filesystem or DB. Never your own modules.
Anti-patternTell
Implementation-coupledIt breaks on a rename even though behaviour didn't change. Look for mocked internals, call counts, or DB queries used to verify.
TautologicalThe expected value is recomputed the way the code computes it. Use a literal, a worked example, or the spec.
Horizontal slicingA batch of tests landed before any code.

Each axis runs in its own parallel subagent. The axes are never merged or re-ranked, and the report gives a worst issue per axis. The repo overrides the smell baseline.

Smell baseline (Fowler, Refactoring ch. 3): Mysterious Name · Duplicated Code · Feature Envy · Data Clumps · Primitive Obsession · Repeated Switches · Shotgun Surgery · Divergent Change · Speculative Generality · Message Chains · Middle Man · Refused Bequest

Gotchas

  • ...HEAD leaves out uncommitted work, so commit before reviewing.
  • Review in a fresh session, because self-review is confirmation bias.
  • The review never converges. Act on the cited findings, then stop.
  • The name clashes with Claude Code's built-in /code-review (a bug hunter). The plugin uses mattpocock-skills:code-review.
  • Subagents can re-invoke /code-review and fan out. When running unattended, watch the agent count.
  • If the agent writes code before the test, that happens. If strictness matters for a slice, watch the run.
  • Write browser and E2E tests after the behaviour works. Put that rule in CLAUDE.md.
