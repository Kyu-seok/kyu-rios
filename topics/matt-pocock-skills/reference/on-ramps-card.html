Never triage your own /to-tickets output. Never use wayfinder for a well-scoped feature.

/triage

  • Each issue gets one category (bug or enhancement) and one state (needs-triage → needs-info, ready-for-agent, ready-for-human, or wontfix).
  • The order: gather context and check whether it's already built or already rejected (.out-of-scope/), then recommend and wait, then verify the claim (reproduce it), then grill if needed, then apply the outcome.
  • ready-for-agent gets an agent brief. ready-for-human means judgement calls, external access, design decisions, or manual testing.
  • An already-built wontfix doesn't go in .out-of-scope/. Only rejected enhancements do.

/diagnosing-bugs

  1. Feedback loop ("this is the skill"): one command, already run, that is red-capable (the exact symptom), deterministic (or a high pinned reproduction rate), fast, and agent-runnable. No loop, no theory.
  2. Reproduce and minimise until every element is load-bearing.
  3. Hypothesise: 3–5, ranked, falsifiable ("if X, then changing Y fixes it"). Show them to the user.
  4. Instrument: one variable at a time, debugger before logs, tagged [DEBUG-xxxx]. For performance problems, measure first.
  5. Fix with a regression test first, at a correct seam. No correct seam is itself the finding.
  6. Clean up: re-run the loop, grep out the debug tags, and put the correct hypothesis in the commit.

/wayfinder

  • A map issue (wayfinder:map) with sections: Destination · Notes · Decisions so far · Not yet specified · Out of scope.
  • Child issues are decision tickets, each sized to about one 100k session, with native blocking. Frontier = open, unblocked, unclaimed.
  • Research (AFK) · Grilling (HITL) · Prototype (HITL) · Task (either).
  • Resolve one ticket per session (research tickets excepted), and claim it first. Make a ticket only for questions you can already state precisely. Everything else is fog.
  • It produces decisions, not deliverables. When the map clears, go to /to-spec.

/prototype

  • Logic question: a single click-through HTML state demo. UI question: radically different variants on one route, switched by a URL param.
  • Throwaway and clearly marked, trivial to run, no persistence, no polish, and it shows the full state after every action.
  • When done, the decision goes into the real code, and the prototype is kept on a prototype/<name> branch, linked from the issue.
