The interview loop

  1. Map the idea as a design tree: decisions branch into the decisions that depend on them.
  2. Frontier = decisions whose prerequisites are settled. Ask all of them in one round.
  3. Each question is numbered, has a recommended answer, and is worded so "yes" accepts it.
  4. Facts → agent (subagent lookup, never ask the user). Decisions → user. A pending lookup only blocks the questions that depend on it.
  5. Recompute the frontier after each round's answers.
  6. Done = frontier empty and user confirms shared understanding. No action before that.

GLOSSARY.md (updated during the interview)

  • Challenge terms that conflict with the glossary. Sharpen overloaded words. Invent edge-case scenarios. Cross-check claims against the code.
  • Write a term in the moment it's resolved, not in a batch at the end.
  • Only project-specific terms. No implementation details or general programming concepts.
**Order**:
A one- or two-sentence definition of what it IS.
_Avoid_: Purchase, transaction

Multiple contexts? Use a root GLOSSARY-MAP.md pointing to one GLOSSARY.md per context.

ADR test: all three, or skip it

  1. Hard to reverse
  2. Surprising without context
  3. A real trade-off

Typical ADRs: architectural shape, integration patterns between contexts, lock-in tech choices, boundary decisions, deliberate deviations, constraints you can't see in the code, rejected alternatives that aren't obvious. Location: docs/adr/0001-slug.md. A single paragraph (context, decision, why) is enough.
