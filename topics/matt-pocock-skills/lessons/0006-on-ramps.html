Lesson 6 · Matt Pocock's Skills

On-ramps and the Detour

Not all work starts as your own idea. Where the work came from tells you where to join the flow.

Your win for this lesson

Given a starting situation, you can choose between /triage, /diagnosing-bugs, /wayfinder, a /prototype detour, or the plain main flow. You can also tell when a bug hunt is ready to start theorising.

0. Warm-up

Question 1 follows up on your AFK question from Lesson 5.

1. Idea one: route by where the work came from

Pocock's router describes one main flow and on-ramps that merge onto it. An on-ramp is "a starting situation that generates work, then merges onto the main flow."[1]

Starting situationReach forMerges back at
Bugs and requests other people filed/triage/implement (it produces agent-ready issues)
Something's broken, and a first glance didn't explain it/diagnosing-bugsThe fix is part of the skill, then /retro
A huge, foggy effort, too big for one session/wayfinder/to-spec
A question in the middle of grilling that talking can't settle/prototype detour (/handoff out and back)The grilling thread you left
Your own idea, which you can hold in one session/grill-with-docsIt is the main flow

Two edges people get wrong:

  • Triage is only for work you didn't create. Tickets from /to-tickets are already agent-ready, so "don't triage them."[1]
  • Wayfinder is for the idea you can't hold in one session. It's "the most cognitively demanding flow here", and it's for exactly that, "never a well-scoped feature."[1]

/triage in one paragraph

It's a small state machine on your tracker. Every issue carries one category (bug or enhancement) and one state (needs-triage, needs-info, ready-for-agent, ready-for-human, or wontfix). Before any grilling, it checks two things: whether the behaviour already exists, and whether a similar request was already rejected (in .out-of-scope/). Then it verifies the claim, for example by reproducing the bug from the reporter's steps. ready-for-human means a person has to do it: judgement calls, external access, design decisions, or manual testing.[2] That's the same AFK/HITL line you asked about.

2. Idea two: no theory without a red loop

/diagnosing-bugs is for the hard ones: "the bug that resists a first glance, the intermittent flake, the regression." The core is Phase 1, building a feedback loop: "This is the skill. Everything else is mechanical."[3]

Phase 1 is done when you can name one command you've already run that meets four conditions:[3]

  1. Red-capable: it asserts the user's exact symptom, not "runs without erroring."
  2. Deterministic: it gives the same verdict every run. For a flaky bug, a pinned, high reproduction rate counts: "A 50%-flake bug is debuggable; 1% is not."
  3. Fast: it takes seconds, not minutes.
  4. Agent-runnable: it runs unattended. A human can be in it only through the shipped hitl-loop script.

"If you catch yourself reading code to build a theory before this command exists, stop." After that the phases are mechanical. Shrink the repro until every part is load-bearing. Write 3–5 ranked, falsifiable hypotheses in the form "if X is the cause, then changing Y will make it disappear," and show them to the user before testing. Change one variable at a time, and tag debug logs ([DEBUG-a4f2]) so cleanup is one grep. Then write the regression test before the fix.

The finding people miss

Only write the regression test at a correct seam, one that reproduces the real bug pattern. "If no correct seam exists, that itself is the finding." The architecture is stopping the bug from being locked down, which is a job for /improve-codebase-architecture (Lesson 7).[3]

3. Idea three: decisions, not deliverables

/wayfinder charts a map, which is one tracker issue whose child issues are decision tickets: "questions whose resolution is a decision, not slices of a build." The map is done when nothing is left to decide. The urge to just start building is "the signal you've reached the edge of the map."[4]

  • The destination comes first, because it fixes the scope. Work beyond it is out of scope, not fog.
  • Fog of war: only make a ticket for questions you can already state precisely. Vaguer ones go in "Not yet specified" until the frontier reaches them.
  • Resolve one ticket per session (research tickets are the exception), sized to about one 100k-token session.
  • When the map clears, it hands off and doesn't build. Go to /to-spec #<map>. Going straight to /implement throws away the linked detail.[1]

The ticket types are where your Lesson 5 question has an official answer:[4]

TypeModeWhy
ResearchAFKIt surfaces a fact, so a subagent runs it in parallel

PrototypeHITLIt makes something rough for you to react to
TaskEitherManual work that unblocks a decision. The agent does it alone where it can; otherwise it gives you a checklist.

/prototype: throwaway code that answers one question

The question decides the shape. "Does this logic feel right?" gets a single HTML file you click through, showing the state after every action. "What should this look like?" gets several radically different UI variants on one route. There are no tests, no polish, and no persistence. "Throwaway" doesn't mean deleted, though. The validated decision goes into the real code, and the prototype is kept as a primary source on a prototype/<name> branch, linked from the implementation issue.[5]

Write the four conditions on a Phase 1 loop. Then write the four wayfinder ticket types, marking each one AFK or HITL.

The loop must be red-capable (asserts the exact symptom), deterministic, fast, and agent-runnable, and you must have already run it once.

Ticket types: Research (AFK), Grilling (HITL), Prototype (HITL), Task (either).
