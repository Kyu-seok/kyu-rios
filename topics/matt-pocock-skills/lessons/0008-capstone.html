Capstone: Your First Real Run

Install the skills, set up one repo, and plan one feature through the whole flow. After this, the teacher is the run itself.

Your win for this lesson

The plugin is installed, Flask/habit-tracker is set up, and you have a written plan for the daily streaks feature. The plan says which skill runs at each step and which boundary move comes after it. Then you run it.

0. Warm-up: everything, mixed

These are drawn from all seven lessons and set in the project you're about to build. No lesson labels.

1. The target: why habit-tracker

A good target is a small app you own, with nothing to lose: a stub, not a finished project. Finished code has history to respect, exercise folders have no single app to grow, and a teaching workspace has no code at all. The target here is habit-tracker, a 17-line Flask app: two routes, templates, and a venv with Flask 3.0. No storage and no tests.

It's a stub with a clear domain (habits, check-ins, streaks). That gives grilling real decisions to make, gives /tdd a real seam (the streak logic), and makes the feature big enough for a few tracer-bullet tickets. It also has no test runner and no guardrail, which /retro will rightly flag. That's useful for you to see.

The feature

Daily streaks: add a habit, check in for today, and see each habit's current streak. Hold the details loosely. Grilling will settle what "a day" means, what breaks a streak, and where data lives. Your job is to answer its questions, not to arrive with a spec.

2. Install and set up (once)

  1. Install the plugin (it updates itself):[1] 
    claude plugin install mattpocock-skills@claude-plugins-official
    Check it with claude plugin list. You'll now see a second teach, because the plugin ships one too. That's harmless.
  2. Open Claude Code in the project: 
    cd habit-tracker && claude
  3. Run /setup-matt-pocock-skills. It explores, proposes, waits for you, then writes.[2] Start with one sentence of context: "Treat Flask/habit-tracker as the project root." If the app lives inside a larger repo, the git root is that parent, so without that sentence it may write its files there.

Drill A: boundary moves on this run

These are the same five questions as Lesson 5, now at your run's real boundaries.

Drill B: the mission, from memory

Write the four failure modes and the fix for each. Then write the main flow with its branches and both on-ramps, without looking at the run plan above.

Failures → fixes: 1. It didn't do what I want → grilling (/grill-with-docs). 2. Way too verbose → a shared language (GLOSSARY.md). 3. The code doesn't work → feedback loops (/tdd, /diagnosing-bugs). 4. Ball of mud → deep modules (/improve-codebase-architecture).

Main flow: /grill-with-docs → (prototype detour via /handoff if talking can't settle it) → multi-session? yes: /to-spec → /to-tickets → /implement per ticket with /clear between (or /implement-spec); no: /implement right there. Inside: /tdd + /code-review. Close with /retro.

On-ramps: /triage (others' issues → /implement), /diagnosing-bugs (→ fix + /retro), /wayfinder (→ /to-spec). Upkeep: /improve-codebase-architecture.
