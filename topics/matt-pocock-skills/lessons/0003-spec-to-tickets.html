From Spec to Tickets

The spec records what you decided. The tickets are the steps that get you there.

Your win for this lesson

Given a breakdown the agent proposes, you can tell a tracer bullet from a horizontal slice, see which tickets are on the frontier, and know what to push back on before anything gets published.

0. Warm-up

From Lessons 1 and 2, answered from memory.

Here's where we are in the flow. Grilling is done. This lesson covers the two steps on the multi-session branch.

1. Idea one: the spec is a decision record

Your snooze grilling is over. You decided on a Channel snooze with fixed presets, decided urgent alerts always get through, and decided to reuse the existing scheduler. All of that lives in one context window that you're about to throw away. /to-spec exists "because context windows end": it writes those decisions down, in your glossary's vocabulary, so a fresh session can pick up the work.[1]

It does not interview you. The skill says "Do NOT interview the user; just synthesize what you already know."[2] The spec records decisions. It doesn't make them. So "if the spec states something you never said, that is a defect."[1]

Seams come first

Before writing any prose, the agent sketches the seams: the places where the feature will be tested. It prefers existing seams, picks the highest one available, and "the ideal number is one." Then it checks the seams with you.[2] For snooze, one good seam is the Notification delivery entry point: given a Notification and its Channel's snooze state, it either sends the Notification or holds it. Take this conversation seriously, because /tdd only tests at seams agreed in advance, and /code-review flags any seam nobody agreed to.[1] You'll see both of those in Lesson 4.

When to skip it, and what to read

Where you areRun
Nothing decided yet/grill-with-docs first
Decided, and it fits in one context window/implement, with no spec
Decided, and it spans several sessions/to-spec, then /to-tickets

On a single-session change, the spec gives you nothing: it's "an extra synthesis step where the model can drift." When you do get a spec, you don't need to read every line. Read the seams and Out of Scope, because a wrong decision in those two places is cheapest to catch now. If the spec surprises you, the grilling wasn't deep enough.[1]

2. Idea two: tracer bullets, not layers

/to-tickets splits the work into tracer bullets, a term from The Pragmatic Programmer. Each slice obeys four rules:[3]

  1. It cuts a narrow but complete path through every layer: schema, API, UI, and tests.
  2. It is demoable or verifiable on its own.
  3. It fits in a single fresh context window.
  4. Prefactoring goes first: "make the change easy, then make the easy change."

Slicing by layer is the rule people break most often. One team ran a 26-ticket stack sliced by layer and needed about twenty agent runs per closed ticket, roughly three-quarters of them rework. Their post-mortem traced every class of failure back to the horizontal slicing.[4]

The one question to ask about every ticket

"What can I demo when this is done?" If the only answer is a layer ("the table exists"), it's a horizontal slice.[4] The opposite failure is the most reported one: twelve tickets for a three-line change. Ask the agent to merge them. If the whole change fits in one context window, you don't need tickets at all.

One exception: a wide refactor, like renaming a column used in thousands of places, can't land green as a vertical slice. It's sequenced as expand → migrate in batches → contract instead.[3] You only need to recognise it for now.

3. Idea three: blocking edges and the frontier

Every ticket declares its blocking edges: the tickets that must be done before it can start. The frontier is the same idea you met in grilling. Any ticket whose blockers are all done can be picked up now.[3] Here's the snooze breakdown:

  1. 01Prefactor: the existing scheduler accepts any delivery callback. No behaviour change.Blocked by: none (can start immediately)
  2. 02Snooze a Channel for 1 hour. Held Notifications arrive when the snooze ends.Blocked by: 01
  3. 03All presets (1h, 8h, 1 week), plus a "snoozed until" label.Blocked by: 02
  4. 04Urgent alerts bypass a Channel snooze.Blocked by: 02
  5. 05A snoozed Channel can be un-snoozed early.Blocked by: 02
  6. 06The settings page lists every snoozed Channel and its end time.Blocked by: 03

Before publishing anything, the agent quizzes you on the numbered list. Is the granularity right? Does each ticket depend only on tickets that genuinely gate it? Should anything be merged or split? "Iterate until the user approves the breakdown." This is the last cheap place to push back.[3]

Where the tickets end up depends on the tracker you configured. In local mode, each ticket is its own file, .scratch/<feature>/issues/NN-slug.md, numbered with blockers first, so /implement 03 works. On GitHub, each ticket is an issue with a native blocked-by link, created as a sub-issue of the spec.[4] Some practical notes from the docs:

  • Run /to-spec and /to-tickets in the same window. Don't clear or compact between them, because a big spec issue can truncate when the agent fetches it back.[4]
  • Dispatch is manual. Count the tickets on the frontier and open that many fresh sessions. /implement doesn't reliably close tickets, so you update their state yourself.[4]
  • The spec gets a ready-for-agent label too. An AFK agent polling that label will try to build the whole spec in one run. Exclude the spec in its prompt, or remove the label.[1]
