The Map: Four Failures, One Flow

Each skill exists because agents fail in a predictable way.

Your win for this lesson

When an agent lets you down, you can name which of the four failures it was and which skill fixes it. You can also walk the main flow from idea to shipped code.

You've already used one

The /teach skill running this course is Pocock's. The copy in ~/.claude/skills/teach is identical to the one in his repo.[1] Its learning records work the same way his ADRs do: short, numbered notes that capture decisions which aren't obvious from the code.

1. Idea one: four failures, four fixes

Pocock describes his repo as "small, easy to adapt, and composable," in contrast to frameworks like GSD, BMAD and Spec-Kit, which "own the process" and "take away your control."[2] Each skill fixes a specific way that coding agents fail:[3]

#FailureRoot causeFix
1"It didn't do what I want"Misalignment. "No-one knows exactly what they want" (Pragmatic Programmer).A grilling session: /grill-with-docs, or /grill-me when there's no repo
2"It's way too verbose"No shared language, so the agent uses 20 words where 1 would doA glossary (GLOSSARY.md), built during /grill-with-docs
3"The code doesn't work"No feedback loops, so the agent is "flying blind"/tdd (red → green; see Lesson 4) and /diagnosing-bugs
4"We built a ball of mud"Agents speed up coding, so they also speed up entropyDeep modules: /improve-codebase-architecture every few days

Failure 2 has a good before-and-after example. Without a glossary: "There's a problem when a lesson inside a section of a course is made 'real' (i.e. given a spot in the file system)." With one: "There's a problem with the materialization cascade."[3]

Link to your last course: /tdd is a computational sensor, and GLOSSARY.md is an inferential guide. Pocock builds a harness out of skills.

2. Idea two: the main flow

Pocock's router skill, /ask-matt, says most work runs along one main flow.[4] Read it from top to bottom:

Three rules hold the flow together:[4]

  1. Grill every time. The README says to use grilling "every time you want to make a change."
  2. Plan in one window, build in fresh ones. Keep grilling, spec and tickets in one unbroken context so they share the same thinking. After that, each /implement starts fresh from its ticket.
  3. Close with /retro. It changes the agent's environment, not the code. Mechanical mistakes become automated checks, and judgement calls become coding standards. This is the steering loop from your harness-engineering lesson.

3. Idea three: who invokes a skill

The catalogue splits skills on one question: who can start this skill?[5]

  • User-invoked skills run only when you type them, like /grill-me or /to-spec. They orchestrate the work. In code, this is disable-model-invocation: true in the frontmatter.
  • Model-invoked skills can also be picked up by the agent when the task fits, like /tdd, /code-review or /grilling. They hold reusable discipline.

There's one rule: a user-invoked skill may call model-invoked skills, but never another user-invoked one. For example, /grill-me is only one line long: "Call the Skill tool with 'grilling'."[6] The user-invoked skill is a thin entry point, and the model-invoked /grilling does the actual work.

4. Practice

Recall: draw the flow from memory

Without scrolling up, write the main flow for a multi-session build: five skills in order, plus the two that run inside each build step.

/grill-with-docs → /to-spec → /to-tickets → /implement per ticket, with /clear between tickets → /retro. Inside each /implement: /tdd, then /code-review. Optional detour after grilling: /prototype.
